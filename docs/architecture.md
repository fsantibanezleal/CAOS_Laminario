# Architecture

How Laminario is put together. Each page covers one part in depth.

| Page | Covers |
|---|---|
| [01 System overview](architecture/01_overview.md) | The processes on the server, what each one does, the offline lane, where data lives. |
| [02 The two data contracts](architecture/02_data-contracts.md) | The ingestion contract (what a submission must satisfy, the licence policy, the flags), the catalog contract (what the web reads, geoprivacy, quality checks), and the committed schemas with their TypeScript mirror. |
| [03 The database](architecture/03_database.md) | SQLite in write-ahead-log mode, the tables, migrations, short ids. |
| [04 The imaging engine](architecture/04_imaging.md) | Reading scanner, TIFF and photo formats; the limits; one measured pyramid per plane; the z-plane policy; extended depth of field (variance selection and complex wavelet fusion, exact against the EPFL plugin, with a defect of the plugin measured and corrected); derivatives without EXIF. |
| [05 IIIF delivery](architecture/05_delivery.md) | iipsrv behind nginx with a tile cache and an access check; info.json with each asset's rights; identifiers; IIIF Presentation 3 manifests with places by geoprivacy; the remote-asset contract and the link check. |
| [06 The processing worker](architecture/06_worker.md) | The durable job queue and journal in SQLite, the worker process and its one-process pool with killing timeouts, crash recovery, the Server-Sent Events stream, the processing jobs and content-addressed storage keys. |
| [07 Accounts and roles](architecture/07_accounts.md) | Invitation-only registration, sessions in a cookie, cross-site writes, password reset, roles and the capability table, contributing a slide case. |
| [08 Uploads](architecture/08_uploads.md) | tus 1.0 through tusd, the pre-create policy (ownership, sizes, quotas, the disk rule), verification in the worker (checksum, sniffing, safe unpacking, a readable header), the source store, tusd in production. |
| [09 The collection tree](architecture/09_collections.md) | Realms, collections, sub-collections and groups; anchors (GBIF backbone, the IMA list with Nickel-Strunz codes, the BGS rock scheme, crystals, materials, parts); the rule semantics; placement by priority; the guard and its overlap test; the taxon cache; the API and IIIF Collections; the 186 icons. |
| [10 The base collection](architecture/10_base-collection.md) | The opening collection: the four open sources, harvest and review sheets, the picks notation, the lock on the GBIF backbone, acquisition by SHA-256 with resumable parallel downloads, offline validation with the floors and the coverage matrix, the bake through the product's own pipeline and the verified import. |
| [11 The interface foundation](architecture/11_interface.md) | The interface's own design system: tokens in OKLCH for two rooms and 18 collection hues, written as sRGB and checked for contrast; three self-hosted faces rebuilt from pinned upstream files; the room and the language painted from the first frame; typed catalogues over Intl; the primitives and their states; the browser gates. |
| [12 Explore](architecture/12_explore.md) | The places a visitor walks: addresses with their filters, focus and scroll on navigation; the realms, cabinets and drawers, the tray at one scale per tray; FTS5 search over a composed text; faceted counts; countries stated or implied; the map over a verified Protomaps extract, labelled in the page's own face; the pointer walk. |
| [13 The slide and the stage](architecture/13_slide.md) | The slide as an object: one layout in millimetres drawn as SVG for the page and as a PDF at 1:1 for print, the QR, plain images; the stage: objectives from the pixel size, the scale bar, planes, polarisers, annotations as W3C Web Annotations; the gates. |
| [14 Contribute](architecture/14_contribute.md) | The account places; a slide case section by section with the slide drawn beside it; validation worded by code in the page's language; a photograph's position read, shown and removed for a private place (and refused by the server if it stays); the pixel size calibrated on a stage micrometer; the files through Uppy and tusd, verified and processed; draft, processing, published; the end-to-end gate. |
| [15 Identify](architecture/15_identify.md) | Identifications, one current per account; every anchor as a lineage; the agreement rule (iNaturalist's community taxon) over every kind; the slide following the community; the badge with the as-good-as-it-can-be vote; flags, hiding and restoring; the Identify and moderation places; the gates. |
| [16 Cabinet and labels](architecture/16_cabinet.md) | Public handles, never the email; the profile's counts and the cabinet (a drawer per collection, the identifications with the community's agreement); one's own export with exact places; label stocks as data, one label fitted to any cell, the sheet from a start position with a printer offset, the test page; the gates. |

Each interface unit adds the page for the places it builds.
